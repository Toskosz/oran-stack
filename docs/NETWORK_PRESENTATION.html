Associações SCTP precisam de um caminho previsível

Modo de falha anterior

SCTP de longa duração pelo overlay de pods

  • O VXLAN do Flannel transportava os pacotes
  • A tradução dos Services envolvia kube-proxy / conntrack
  • Associações N2 e F1 podiam oscilar após o setup
Solução atual

Domínios L2 dedicados via Multus

  • Cada endpoint SCTP recebe um IP secundário estático
  • Bridges OVS conectam os pods diretamente
  • VXLAN estende cada bridge entre os nós
Regra prática: HTTP e UDP permanecem nativos de nuvem; N2, F1-C e E2AP saem do overlay primário.

Limites do Kubernetes

PSS baseline

Nenhuma NetworkPolicy está definida.
  • A separação por namespace é organizacional
  • As bridges OVS dividem o SCTP em domínios L2
  • Namespaces das NFs permitem workloads privilegiados
  • A UPF exige NET_ADMIN, TUN e encaminhamento IP

O isolamento hoje = namespaces + limites de bridge, não NetworkPolicies entre pods.

SCTP era apenas a primeira etapa do registro E2

Falha 1 · etapa 2

Identidade RMR incorreta

O e2mgr usava o hostname variável do pod, mas as rotas esperavam ric-e2mgr.

Correção: definir RMR_SRC_ID=ric-e2mgr.

Falha 2 · etapa 3

Redis incompatível com o RNIB

O Redis genérico não implementava o comando O-RAN MSETMPUB; o estado CONNECTED não era salvo.

Correção: usar ric-plt-dbaas:0.6.5.

Como interpretar: SCTP ESTABLISHED prova o transporte; gnb_001_001_00019b CONNECTED prova o Setup E2; RIC Indication Received prova o caminho KPM completo.

Gates de implantação

Jobs do Kubernetes comprovam o funcionamento ponta a ponta

Gate 1 · E2

verify-e2

Consulta o e2mgr pelo ID do gNB configurado.

Se o e2term estiver saudável, mas o registro estiver ausente, pode reiniciar a CU e depois a DU uma vez antes de falhar.

Gate 2 · xApp

xapp-lifecycle

Exercita AppMgr, RTMgr, assinaturas e rotas RMR.

A condição final de sucesso inclui o recebimento de uma indicação KPM.

verify-ue

Lê os logs do sidecar srsUE.

Exige RRC Connected e PDU Session Established.

Fontes: kubectl logs AMF/CU/DU/srsUE · verify-e2 · verify-ue · captura 14/08 12:07Z26

Por que o UE não conectou?

O socket abriu, mas o UE não encontrou a célula

Ponto exato da falha
  • 1 · Transporte: ZMQ/TCP ESTAB nas portas 2000 e 2001
  • 2 · Sincronismo PHY: UE permanece em IDLE
  • 3 · Acesso aleatório: nenhum PRACH enviado
  • 4 · Controle: nenhum RRC Connected
  • 5 · Core: nenhum Registration Request ou sessão PDU

ZMQ ESTAB prova que os sockets existem, mas não prova que o UE recebeu amostras IQ válidas e decodificou a célula.

Erro observado nos logs

PHY-SA SYNC state=IDLE tti=0

Discarding samples and sending tx_end

NAS5G: DEREGISTERED / PLMN-SEARCH

  • Sem PSS/SSS, MIB, SIB ou Found Cell
  • CU permaneceu com num_rrc_ues=0
  • AMF não recebeu tentativa de registro do UE

Causa localizada, mas não encerrada: incompatibilidade ou configuração no caminho PHY/IQ entre OCUDU release_26_04 e srsUE 25.10.0. Os dados não provam ainda qual parâmetro ou implementação é a causa raiz.

Fontes: logs srsUE/CU/AMF · sockets ZMQ · collect-ue-diagnostics.sh · duas corridas em 14/0827
