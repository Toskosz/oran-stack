Justificativa do projeto

Associações SCTP precisam de um caminho previsível

Modo de falha anterior

SCTP de longa duração pelo overlay de pods

  • O VXLAN do Flannel transportava os pacotes
  • A tradução dos Services envolvia kube-proxy / conntrack
  • Associações N2 e F1 podiam oscilar após o setup
DNAT conntrack perda de associação
Solução atual

Domínios L2 dedicados via Multus

  • Cada endpoint SCTP recebe um IP secundário estático
  • Bridges OVS conectam os pods diretamente
  • VXLAN estende cada bridge entre os nós
L2 direto IP de bind estático sem DNAT de Service
Regra prática: HTTP e UDP permanecem nativos de nuvem; N2, F1-C e E2AP saem do overlay primário.

Defeito 1 · identidade RMR

RMR_SRC_ID=ric-e2mgr

Sem isso, o RMR usa o hostname do pod. As rotas do rtmgr exigem o remetente ric-e2mgr:3801; o e2mgr fica com open=0 / succ=0 rumo ao e2term.

Defeito 2 · backend RNIB

DBAAS OSC, não Redis de estoque

redis:6-alpine não implementa MSETMPUB. O e2mgr falha a escrita CONNECTED e retorna sem enviar 12002. A imagem é ric-plt-dbaas:0.6.5.

Dois planos, dois IPs

local-ip do e2term é o IP Flannel do pod. SCTP E2AP usa 10.200.3.4 em e2br. Trocar os dois quebra o keepalive.

TCP ≠ RMR saudável

Conectar em ric-e2term:38000 só prova o listener. Rotas, identidade de origem e RNIB ainda podem falhar em silêncio.

A CU não retenta

wait-for-e2t atrasa o start. Se o E2T existe e o gNB não, verify-e2 reinicia CU e depois DU uma vez.

gnb_001_001_00019b CONNECTED prova o Setup E2 — não o caminho de indicações KPM (12050).

O que este laboratório não implementa

O1 / SMO Ausente

Sem caminho de gerenciamento NETCONF nem integração SMO.

O2 Ausente

Sem interface de infraestrutura O-Cloud.

E1 Local

A1 Pronto

  • Sem rádio físico externo

  • Endereços Docker legados 172.20/21/22 não são a fonte de verdade do Kubernetes

Roteiro

De um laboratório estático a uma plataforma O-RAN dinâmica

01 · Ciclo de vida dinâmico do gNB

Descobrir nós em tempo de execução

Usar o e2mgr como fonte de verdade, alocar IDs de gNB e endereços Multus únicos, e verificar um conjunto conectado esperado em vez de um ID fixo.

02 · Entrega RMR durável

Estabilizar o roteamento de indicações

Corrigir a configuração de identidade de RTMgr, SubMgr, A1Mediator e RMR para que as rotas 12050 sobrevivam sem laços de re-POST ou reinícios do E2Term.

03 · Vários xApps simultâneos

Adicionar aprendizado seguro no RTMgr

Dar a cada xApp um release e FQDN de Service únicos, adicionar descoberta de rotas a quente e preservar indicações dos xApps existentes durante o onboarding.

04 · Avaliação E2 do CU-CP

Reavaliar o suporte RAN mais recente

Catalogar métricas KPM do CU-CP, comparar o comportamento de CU-CP e CU-UP, e definir um padrão respaldado por versão para a seleção de nós pelo xApp.

Estado-alvo: implantação a frio, nós dinâmicos, vários xApps e indicações KPM contínuas — sem reparo manual com kubectl.
